## 1. 三分模型（不是二分）

灰色地带之所以灰，是因为硬塞进「系统 vs 场景」二分。真相是有第三类——共享基建。

| 类别 | 归属 | 典型 |
|---|---|---|
| ① 功能 | 系统负责人（C） | 记忆卡片面板、回答框、生长动画、连线弹窗、家庭画像木牌、房间生成入口/反馈、季节氛围、toast 逻辑、数据层、AI 客户端层 |
| ② 场景 | 场景认领人（按 36 号） | `.tscn` 结构、美术资产、Y-Sort 摆放、碰撞、场景内布局 |
| ③ 共享基建 | 走 maintainer 模型（§3） | UI 主题/字体/按钮样式、player.gd、输入映射、manifest、场景切换框架 |

> 关键区分是 **「功能」vs「场景」**，不是「碰不碰 UI/动画」。
> 系统负责人为自己的功能**前端到后端整条链路自己做完**——这包含功能性 UI/动画
> （它们是系统功能的前端表现，不是场景搭建）。

---

## 2. 判定试金石（任何一段灰色代码，问这几句）

1. 它是**跨场景复用的功能表现**（面板 / 动画 / 反馈逻辑）吗？→ **① 功能**
2. 它是**某个具体场景内**的结构 / 美术 / 碰撞 / 布局吗？→ **② 场景**
3. 它**多人都依赖、不属于任何单一功能或单一场景**吗？→ **③ 共享基建**
4. 还分不清 → **群里 5 分钟一句话定，结论记进本文 §5 或变更日志**（一次性消除，定了不再争）。

---

## 3. ③ 共享基建的治理模型（轻量两条）

每块共享基建指定**一个 maintainer**（负责保持一致性、API 稳定、做大改），但：

- **纯使用**（调 toast、套面板样式、读 input、按 manifest 落点挂功能）→ **随便用，不用通告**。
- **改接口 / 行为**（不只是用）→ **群里一句话 + 记一行变更日志 + maintainer 点头**（沿用 36 号 §1.3）。

> maintainer 怎么定：**谁建的 / 谁最常改 → 谁当**，基于现实不靠分配。

---

## 4. 最高优先级红线：「不重写」清单（独立于上面，压倒一切）

36 号 / 31 号已定的 **Player / 移动 / 输入 / 场景切换 / 云端上传** = **冻结共享件**：
可封装、可扩展，**不可推倒重写**。连 maintainer 也不能擅自重写，要改走 PR + 原作者评审。

## 5. 已知灰色地带的 maintainer（2026-06-28 群里确认）

| 灰色块 | 建议 maintainer | 理由 |
|---|---|---|
| UI 框架（toast / 面板主题 / 字体 / 按钮样式，在 `SceneManager`） | C（系统） | C 建的、功能 UI 最常用 |
| `player.gd` / 移动 / 输入 | 原作者，默认只读（冻结件） | 36 号"不重写" |
| manifest **坐标**（slots / zones / portals 的 pos） | 场景认领人 | 落点是场景的 |
| manifest **schema / 字段** + 数据契约（docs/04、表结构） | C（系统） | 数据结构是系统的 |
| `ScenePortal`（场景切换框架） | 原作者 | 框架，改行为走通告 |
| 各场景 `.tscn` | 各场景认领人 | 一人一场景 |

> 已确认生效。后续如需调整某块 maintainer，群里一句话定 + 更新本表即可。

## 6. 对接面：功能怎么"挂"进场景

系统负责人做的功能要落进场景里，**唯一对接面 = manifest（slots / zones / portals）+ 数据层方法**：

- 场景认领人在 manifest 里定落点坐标（slot / zone / 木牌位 / 入口）。
- 系统负责人的代码**读 manifest** 把功能（记忆花 / 家具 / 木牌 / 连线 / 入口）挂上去。
- **坐标归场景、逻辑归系统**——所以 `zones_room.json`、family-portrait 木牌挂载点等
  由系统先用临时值跑通，**待场景背景定稿后由场景认领人 + C 校准坐标一次并冻结**。
