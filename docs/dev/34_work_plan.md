## Part 0 · 协作与解耦原则（B/C 将来拆给两个人,现在就埋好结构）

当前 B(AI+内容安全)与 C(游戏系统+后端)暂由同一人迭代,之后会拆给两个不同的人。因此写代码与排期必须保证两模块能被干净拆开、不留缠绕。

- B 的所有产物只在 `backend/ai/`、`backend/mocks/`;C 的所有产物只在 `game/scripts/`、`game/scenes/`。

## Part 1 — 项目解读

### 1.1 是什么
AI 驱动的"数字家庭第三空间"。家庭成员上传照片/留言/明信片/房间照片 → AI 整理成记忆卡片并提温和问题 → 家人补充回答 → 记忆在花园/鱼塘/农场/个人房间/老街等**预制场景**里变成可点击、会生长的节点。核心:**让家庭记忆长成花园**。

### 1.2 核心闭环
```
上传记忆 → AI 生成记忆卡片 → AI 提温和问题 → 家人回答 → 地图生成记忆节点 → 花园逐渐生长
```
成功标准(立项第十三条):定位清楚、闭环完整、视觉有记忆感、AI 使用合理、演示稳定。**稳定 > 功能多**。

### 1.3 关键设计约束
- **AI 只整理不编造**:禁编造家庭事实/推断关系/心理诊断/煽情/死亡疾病离婚创伤;不确定用"可能/看起来像"。
- **AI 不输出坐标**:只给 `suggested_scene` / `node_type` / `object_type` / `zone`;真实坐标(`slot_id`、footprint)由 SlotManager 决定。这是 B/C 接口分界线。
- **场景是预制"记忆容器"**,不是 AI 现生成地图。
- **每个 AI 功能必须有 mock/fallback**,接口挂了也能演示、不崩。
- **坐标系**(docs/09):逻辑 1280×720 固定,美术源 640×360,2x 显示,Nearest;定位点 bottom_center;slot 偶数、对齐 16px。

### 1.4 P0 / P1 / 不做(docs/01,含调整)
- **P0(必须)**:进花园 / 上传建 memory / AI 记忆卡片 / 用户回答 / 地图生成节点 / 花园 Hub / 爸爸鱼塘(漂流瓶) / AI 房间生成(≥3 物件) / 记忆卡片 UI / 失败兜底。
  - **提升进 P0 的情感时刻**:① 回答确认后的**记忆生长动画**(种子→花苞→开放,≤3 秒);② **花园背景按"跨成员回答次数"分季**——一个成员回答了另一个成员上传的记忆算一次跨成员互动,**0 次→春天 / 3-5 次→夏天 / 10 次以上→秋天**。繁茂度 = 家庭关系温度计,直接服务"促进家庭交流"。这两项是演示"哇"时刻,不降级到 P1。
- **P1**:爷爷农场 / 老街胡同 / 旅行区域 / 记忆树 / 成员头像。
- **不做**:战斗/开放世界/AI 恋爱/养成/装修商城/实时聊天/3D 重建/AI 心理分析/编造事实/支付。
- **降级顺序**:场景只保花园+鱼塘+AI 房间;AI 挂了用 mock;云端挂了用本地兜底。

### 1.7 参赛差异化亮点(给评委的记忆点)
普通 AI 游戏止步于"单图→结构化提取"。本作差异化在于 **AI 把离散记忆织成有温度的关系网络**,并让这种"织"在画面里被看见:
- **跨记忆关联**:每上传一条记忆,AI 增量发现它与已有记忆的隐藏联系,在花园里长出"记忆连线"+ 关联问题——记忆景观从一堆点变成一张网的瞬间。
- **家庭气质画像**:AI 用一句话概括家庭共同偏好(不评判关系),挂入口木牌,让评委一进场就感到"这是某个真实家庭"。
- **个性化 + 定向漂流瓶**:问题贴合家庭真实记忆分布;还能定向投给指定家人,把单向上传变成双向对话。
- **生长动画 + 分季花园**:把"记忆在生长、关系在升温"从口号变成可见的视觉情感高潮(分季按跨成员互动数,而非记忆数量)。
- **可见的诚实**:记忆卡片上 AI 推测内容用浅灰斜体 + 问号、家人确认内容用深色——把"AI 只整理不编造"从后台规则变成画面里看得见的诚实,这是内容安全的差异化可视化表达。

> 所有新能力严守约束:有 mock/fallback、输出符合 docs/04 契约风格(枚举+结构化 JSON+禁编造)、AI 不输出坐标、不进"不做"清单、不放宽 Gate 验收。

### B — AI 模块与内容安全
**独占文件清单**:`backend/ai/`(云函数实现 + system prompt)、`backend/mocks/`(6 套 mock)、`docs/04`(契约 + 变更日志)。**不得**触碰 `game/`。
**基础三接口**(docs/04 契约):
- `POST /api/ai/generate-memory-card` 照片/文字 → 记忆卡片
- `POST /api/ai/generate-bottle-question` 场景 → 温和问题(**增强:个性化 + 定向投递**)
- `POST /api/ai/analyze-room-photo` 房间图 → 类型/氛围/物件
**新增/增强 AI 能力**(同样:Serverless、JSON 校验+清洗、内容安全过滤、mock 兜底、禁坐标禁编造):
- **`POST /api/ai/cross-memory-link`(跨记忆关联,增量驱动)** — **触发:每当新上传一条记忆**,AI 只扫描这条新记忆与已有记忆的关联(增量,不到 N 条一次性全扫),让关联随上传自然浮现。输入 `{family_id, new_memory_id}`,输出:
  ```json
  {
    "links": [
      { "memory_id_a": "mem_new", "memory_id_b": "mem_007",
        "relation_type": "same_place|same_people|same_theme|same_era",
        "confidence": 0.78,
        "question": "这两张照片好像都在同一片水库，你们是同一次旅行吗？",
        "node_type": "memory_link" }
    ],
    "safety_note": "仅依据画面/文字的可见重叠，未推断人物关系。"
  }
  ```
  只给 memory_id 对 + 关联类型 + 问题;连线坐标由 C 按两端节点 slot 计算,B 不输出坐标。**该接口为异步、非阻塞调用**:上传记忆后记忆花立刻出现,不等关联结果;连线等 AI 返回后再"悄悄长出来"。比赛期不做节流,但须在 docs/04 该接口注释里留一句"将来量大时可加节流",作为已知技术债记录。
- **`POST /api/ai/family-portrait`(家庭气质画像,事件驱动)** — **触发:有新成员第一次参与,或记忆总数翻倍(2→4→8→16)**时才重算一次,避免每次上传都算。输入 `{family_id}`,输出 ≤30 字共同偏好/场景描述(不评判关系):
  ```json
  { "portrait": "一个爱往水边跑、喜欢热闹饭桌的家庭", "confidence": 0.7,
    "safety_note": "仅描述共同偏好，未评价家庭关系或个人。" }
  ```
  显示在花园入口木牌。
- **个性化 + 定向漂流瓶**:`generate-bottle-question` 输入扩展为带家庭 `memory_type`/`scene` 分布统计 → AI 出专属问题(如 fishing 类多 → 问钓鱼回忆);并支持**定向投递**:用户答完一段记忆后可选"想听听某位家人怎么说",请求带可选 `target_member_id`(空=漂流/非空=定向),输出沿用契约,数据层由 C 在 `bottles.target_member_id` 落地。
**内容安全**:统一过滤层(禁编造/关系推断/诊断/煽情/坐标);不确定用"可能/看起来像";所有输出 JSON 校验+字段清洗。Key 走 Serverless,绝不进前端/仓库。
**mock(解耦关键资产)**:6 类输出(基础 3 + cross-link + portrait + 个性化/定向 bottle)各备 mock,**与真实输出严格同构、字段完整、内容贴近真实**(非空壳),让将来的 C 靠 mock 即可独立开发。
**演示固定结果(最后一道防翻车保险)**:一组**写死的、对应 Part 5 故事各步的 JSON + 图片**,与普通 mock 区分——普通 mock = 随便给个合法返回;演示固定结果 = 必须讲出最终选定的那个具体故事。存放于独立目录 **`backend/mocks/demo_script/`**,按步骤编号组织(`step1`…`stepN`)。B 负责内容,C 负责读取与"演示模式"开关(见 Part 2-C);触发:接口异常或显式演示模式时直接读这套数据,保证故事一定能完整跑完。**目录结构与 JSON 格式在阶段 1 就定下来;具体写死内容待 Part 5 故事后期定稿后(阶段 4 前)回填**——定稿前可先用参考示例占位,跑通演示模式链路。
**规范**:docs/04(全)、docs/05(§6)、docs/09(§8 房间生成边界)、docs/dev/32。

### C — 游戏系统与后端稳定
**独占文件清单**:`game/scripts/`、`game/scenes/`、`game/assets/manifest/` 中 C 列字段(display 尺寸/click_rect/collision_rect/slot/portal JSON)、`backend/supabase/`(schema SQL)。**AI 客户端层**(`game/scripts/` 下调云函数 + 失败回退 mock 那一层)**归属 C**,但它消费的**契约归属 B**——依赖方向:C 客户端 → 依赖 → B 的 docs/04 契约;契约变更由 B 发起、按 0.2 流程同步。
- 保现有 MVP 稳定的前提下接入记忆系统。
- **(前置)`main.gd` 拆分**:把 2583 行按功能拆成独立 **autoload Manager**(至少 MemoryManager / CloudManager / SceneManager),**只搬代码不改逻辑**;之后新系统挂对应 Manager,不再直接扩 `main.gd`。
- **数据库扩展**:memories / nodes / **bottles(含 `target_member_id`,可空)** / answers / rooms / room_objects(docs/05 §3)+ RLS;**`families`(或等价家庭级表)新增 `cross_member_interaction_count`(整数,默认 0)**——每次有效跨成员回答 +1,进花园直接读它判断季节,不实时 join 聚合。**此字段必须在阶段 0 冻结 schema 时就设计进去**,不能拖到 Gate 2 再加(否则要改已上线表结构)。
  - **"有效跨成员回答"定义**:回答者 ≠ 该 memory 的上传者,且**同一人对同一条 memory 的重复回答只计一次**(防刷数据制造假繁茂)。

## Part 5 — 演示故事脚本（⏳ 待定 · 项目后期确定）

**参考示例(非最终)——主角设定**:奶奶 72 岁,独居老家小院;孙女 20 岁,在北京读大学。两人平时只在微信问"吃了吗"。

**参考示例——一镜到底的演示流程**：

1. **开场**——孙女登录,花园还很空旷(尚无跨成员互动,**春天稀疏背景**)。她上传一张小时候和奶奶在老家院子的旧照片;**同时帮奶奶上传了一张奶奶家灶台的照片**(作为后续 analyze-room-photo 的输入来源,房间生成由此而来)。
   *截图建议①:空旷的春日花园 + 上传面板(两张照片)。*
2. **AI 记忆卡片(可见的诚实)**——AI 为院子照生成卡片:标题《老院子的午后》,描述只写画面可见物(院墙、石桌、一棵树);**AI 推测项"可能是 1990 年代"以浅灰斜体 + 问号显示**,提出温和问题:**"这个院子里,你最记得的是什么气味?"**
   *截图建议②:记忆卡片 UI,浅灰斜体推测项 vs 深色确认项对比清晰。*
3. **奶奶第一次进游戏**——她在花园看到一个待回答的记忆花(花苞状),点开看到孙女上传的照片和那个问题,回答:**"槐花香,你小时候总在树底下睡着。"**(此即一次**跨成员回答**)
   *截图建议③:奶奶视角,花苞节点 + 回答框。*
4. **情感高潮(哇时刻)**——回答确认瞬间,**记忆花触发生长动画:种子→花苞→开放,3 秒内一棵槐树在院子记忆旁长出**;卡片里"槐花香"从 AI 留白变成**奶奶确认的深色文字**,配乐轻轻上扬。
   *截图建议④:生长动画三连帧 + 文字由灰转深的前后对比。*
5. **场景解锁(房间生成有出处)**——这段两代人共同完成的记忆,**解锁奶奶的个人农场场景**:基于第 1 步那张灶台照片,AI analyze-room-photo 已识别并由 RoomLayoutManager 摆好土灶、竹篮、腌菜坛(≥3 件)。孙女走进去,像第一次"看见"奶奶的生活空间。
   *截图建议⑤:灶台照片 → AI 生成的奶奶农场小屋,前后对比。*
6. **双向对话(定向漂流瓶)**——奶奶答完后选了"想听听孙女怎么说",一个**定向漂流瓶投到孙女花园**,问"你还记不记得院子里那棵树?";孙女回瓶,两人一来一回。随上传增多,AI **增量**拉出一条**记忆连线**,把"老院子"和另一张"奶奶在河边洗衣"的照片连起来,浮出"这两处是不是同一个村子?";跨成员互动累积后,入口木牌浮现**家庭气质画像:"一个守着老院子、把日子过得有香味的家庭。"** 此时花园已从春转入更繁茂的季节(跨成员互动数上升)。
   *截图建议⑥:定向漂流瓶在孙女花园 + 记忆连线 + 入口木牌画像;⑦:完整用户旅程图。*

**结尾文案方向**:没有人被要求"好好沟通",但奶奶和孙女在一座慢慢长出来、会随互动升温的花园里,重新开始讲述彼此的故事。**Family Garden 让家庭记忆,长成一座会生长、会自己织网的花园。**

## Part 6 · 风险与回退总表

目的:让全员对"哪些能砍、哪些绝不能砍"有共识,防止临近截止为非核心功能把主线搞崩。

> **绝对不能砍的 P0 主线**:上传 → 记忆花 → 卡片 → 回答 → 生长动画。这条断了,作品就不成立。其余功能砍掉后演示仍应成立。

| 功能 | 若做不出来/做晚了的后果 | 演示是否仍成立 | 兜底方案 |
|---|---|---|---|
| **P0 主线**(上传→记忆花→卡片→回答→生长动画) | 作品核心闭环不成立 | ❌ **不成立,绝不可砍** | 无可退;所有资源优先保它 |
| **记忆生长动画** | 失去情感高潮"哇"时刻,演示平淡 | ⚠️ 勉强成立但大幅减分 | 降级为简单淡入/缩放出现,仍保"长出来"感 |
| **cross-memory-link**(跨记忆关联) | 少一个差异化亮点(记忆织网) | ✅ 成立 | 异步非阻塞,做不出直接不渲染连线;演示用 `demo_script` 写死一条连线 |
| **family-portrait**(家庭画像) | 入口木牌少一句点睛 | ✅ 成立 | 木牌显示静态默认文案;演示用 `demo_script` 写死那句画像 |
| **AI 房间生成** | 少一个 P0 展示项 | ⚠️ P0 要求,尽量保 | RoomLayoutManager 回退**预设房间**;演示用 `demo_script` 对应步骤的房间固定结果 |
| **定向漂流瓶** | 双向对话变单向上传 | ✅ 成立 | 退化为普通漂流瓶(target_member_id 留空);演示用 `demo_script` 串双向 |
| **真实 AI 接口**(全部) | 无法现场实时生成 | ✅ 成立 | 每接口 mock 兜底;演示模式直接走 `demo_script` 固定结果,故事照跑 |
| **Supabase 云端** | 数据无法保存/读取 | ✅ 成立 | 本地存档兜底 + 预设家庭/记忆/房间;刷新用本地数据继续演示 |
