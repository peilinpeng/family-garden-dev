# 32｜Claude / Cline / CodeBuddy 协作规则

## 1. 目的

本文档用于规范使用 Claude、Cline、CodeBuddy 等 AI coding 工具时的协作方式，避免 AI 误删、误改、过度重构或破坏已有 MVP。

AI 是开发搭档，不是无限制自动驾驶。每次任务都必须有明确范围、输入文件、输出要求和验收标准。

---

## 2. 每次给 AI 的任务格式

建议使用以下模板：

```text
请读取以下文档/文件：
1. ...
2. ...
3. ...

当前目标：
...

本次任务范围：
...

不允许改动：
...

期望结果：
...

验收标准：
...

请先给出修改计划，不要直接大规模改代码。
```

---

## 3. AI 修改代码前必须做什么

AI 在修改前必须：

1. 阅读相关文件；
2. 总结现有结构；
3. 指出将修改哪些文件；
4. 说明为什么要改；
5. 给出风险；
6. 等待确认，除非任务非常小且明确。

---

## 4. 什么时候可以直接改

可以直接改：

- 文案小修；
- 新增独立 mock JSON；
- 新增独立 markdown 文档；
- 新增一个不影响主流程的独立脚本；
- 修复明确的单点 bug。

必须先确认：

- 重构目录；
- 改全局状态；
- 改数据结构；
- 改上传逻辑；
- 改主场景；
- 改 AI 接口字段；
- 删除文件；
- 替换引擎；
- 回退版本。

---

## 5. 红线

AI 不允许：

1. 回退 main；
2. 删除已有可运行功能；
3. 为“更优雅”推倒重来；
4. 未确认就换技术栈；
5. 未确认就改 AI JSON 字段；
6. 未确认就修改多个核心场景；
7. 把 API Key 写进前端；
8. 删除 mock/fallback；
9. 忽略移动端测试；
10. 编造不确定的 API 用法。

---

## 6. 推荐 AI 工作流

### 6.1 设计阶段

让 AI 做：

- 架构评估；
- 数据流设计；
- 场景拆分；
- 任务拆解；
- 风险清单；
- prompt 设计。

### 6.2 开发阶段

让 AI 做：

- 小模块实现；
- mock 数据；
- 接口封装；
- UI 面板脚本；
- 节点生成逻辑；
- bug 定位。

### 6.3 联调阶段

让 AI 做：

- 检查数据字段；
- 检查文件引用；
- 查找崩溃原因；
- 生成测试清单；
- 写 fallback。

### 6.4 提交阶段

让 AI 做：

- 文档整理；
- 演示脚本；
- README；
- 提交检查表；
- bug triage。

---

## 7. 单任务提示词示例

### 7.1 开发鱼塘场景

```text
请读取 docs/00_project_overview.md、docs/scenes/11_scene_fishpond.md、docs/ui/21_ui_bottle_panel.md。

任务：实现鱼塘场景最小可运行版本。

范围：只新增/修改鱼塘相关文件，允许新增 mock bottle JSON。

不允许：不要改家庭花园主流程，不要改 AI 接口字段，不要重构全局状态。

验收：能进入鱼塘，点击漂流瓶打开问题面板，输入回答后生成一个 mock 记忆节点。

请先列出修改计划和文件列表。
```

### 7.2 接入 AI 记忆卡片

```text
请读取 docs/04_ai_interfaces.md 和当前 AI client 相关文件。

任务：实现 generate-memory-card 的接口封装。

要求：AI 失败时返回 mock 数据；输出字段必须符合 docs/04_ai_interfaces.md；不要把 API Key 放前端。

请先检查当前项目是否已有 API client，再给出最小修改方案。
```

### 7.3 检查上传 bug

```text
请检查当前图片上传相关代码。

问题：用户可以打开文件选择器，但选择文件后 UI 没有显示 selected file，并且无法真正上传到云存储。

要求：不要回退 main，不要重写整个上传系统。请先定位根因，再给出最小修复方案。
```

---

## 8. 验收方式

每次 AI 修改后必须输出：

1. 修改了哪些文件；
2. 新增了哪些文件；
3. 没有修改哪些敏感模块；
4. 如何运行；
5. 如何测试；
6. 已知风险；
7. 如果失败如何回退。

---

## 9. 多 AI 工具并行规则

如果同时使用 Claude、Cline、CodeBuddy：

- 不要让多个 AI 同时改同一文件；
- 一个任务一个 AI；
- 一个模块一个分支；
- 每次合并前看 diff；
- 每次合并后跑主流程；
- 每晚保留一个稳定版本。

---

## 10. AI 不确定时的要求

如果 AI 不确定某个技术点，必须说不确定，并给出验证方式。

例如：

- Godot Web 在微信浏览器能否上传图片；
- Unity WebGL 在移动端加载速度是否可接受；
- 腾讯云 COS 预签名 URL 的具体实现；
- Supabase 与 COS 混合使用的权限问题。

不允许编造。

---

## 11. 项目统筹者使用建议

项目统筹者每次给 AI 任务时，尽量只给：

- 一个目标；
- 一个场景；
- 一个接口；
- 一个 bug。

不要一次性要求 AI “做完整游戏”。

最稳方式：

```text
理解现状 → 小步计划 → 修改一个模块 → 验收 → 再进入下一个模块
```
